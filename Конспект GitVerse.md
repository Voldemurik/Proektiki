Полный конспект по всем вкладкам официальной документации GitVerse (gitverse.ru/docs), кроме «Приобретение лицензий и подписок» и «Примечания к обновлениям». Структура повторяет вкладки документации с разбивкой по блокам до 2–3 уровней.

# 1. Вкладка «GitVerse»

## 1.1. Основы и начало работы

### Обзор

GitVerse — российская платформа для хостинга Git-репозиториев и совместной разработки: репозитории, запросы на слияние, задачи, вики, CI/CD, пакетный реестр, Pages, AI-инструменты (GigaCode), организации и команды.

### Быстрый старт

- Регистрация аккаунта → создание репозитория (название, описание, видимость публичный/приватный, README, .gitignore, лицензия).
- Клонирование по SSH (`git@gitverse.ru:owner/repo.git`) или HTTPS; базовый цикл: clone → ветка → коммит → push → запрос на слияние.
- Поиск (Обзор) — по репозиториям, пользователям и организациям; глобальный поиск по коду внутри репозитория.

### Справочная документация

- **Глоссарий** — термины платформы (репозиторий, форк, запрос на слияние, раннер, артефакт и т.д.).
- **Поддерживаемые браузеры** — актуальные версии Chrome, Firefox, Safari, Edge, Яндекс Браузер.
- **Поддерживаемые языки** — подсветка и определение языков в интерфейсе.
- **FAQ** — базовые вопросы по платформе.

## 1.2. Учетная запись и профиль

### Быстрый старт

Регистрация, заполнение профиля, настройка видимости.

### Практические руководства

- **Управление аккаунтом** — смена логина (требует обновления URL удаленных репозиториев: `git remote set-url`), удаление аккаунта.
- **Эл. адреса** — несколько адресов на аккаунт, основной адрес, верификация.
- **Уведомления** — настройка каналов (веб, email), подписки на события репозиториев.
- **Персонализация** — тема интерфейса и прочие пользовательские настройки.
- **Закрепление репозиториев** в профиле пользователя.
- **Заполнение профиля** — имя, био, аватар, ссылки, местоположение.
- **Видимость пользователя**: публичный (виден всем, включая неавторизованных), внутренний (только авторизованным), приватный (не ищется в Обзоре; профиль виден взаимным подписчикам и участникам общих организаций; можно добавлять в соавторы и организации; репозитории не ищутся и доступны только соавторам).

### Справочная документация

- **Дашборд** — лента событий, задачи и запросы, требующие внимания.
- **Лимиты** — просмотр квот пользователя (LFS, пакеты, релизы).
- **Профиль**: вкладки Обзор, Репозитории, Пакеты, Подписки, Избранное.

## 1.3. Ранний доступ

- **Открытый ранний доступ** — функции, доступные всем желающим (включаются в настройках).
- **Закрытый ранний доступ** — функции по списку доступа (например, корпорации, сессии GigaCode, GigaCode-разработчик).

# 2. Вкладка «Совместная работа»

## 2.1. Аутентификация

### Работа по SSH

- Рекомендуемый тип ключа — **ed25519**: `ssh-keygen -t ed25519 -C "email"`.
- Публичный ключ добавляется в настройках профиля → SSH-ключи. Проверка: `ssh -T git@gitverse.ru`.
- **Отпечатки SSH-ключей сервера** — для сверки при первом подключении (ключ сервера SHA256: `SHA256:IL4khwaSrT4uHCu9LTUW7dRJyMB5XkOJnFrP0nmdMXU`).

### Работа по HTTPS

- Клонирование/пуш по HTTPS с логином и **токеном доступа вместо пароля** (пароль аккаунта для Git не используется).

### Токены

- Создаются в разделе «Управление токенами»; показываются один раз — сохранять сразу.
- При создании выбираются сущности и права (Чтение/Запись) — тот же механизм используется для Публичного API и GitVerse MCP.

### Ключи развертывания (deploy keys)

- SSH-ключи уровня репозитория для read-only доступа с серверов/CI, без привязки к аккаунту пользователя.

### Проверка подписи коммитов (GPG)

- Цикл: проверка существующих ключей (`gpg --list-secret-keys`) → генерация нового (RSA 4096) → связывание email с ключом → добавление публичного ключа в аккаунт GitVerse → настройка Git (`git config user.signingkey`, `commit.gpgsign true`) → подписание коммитов (`git commit -S`). Подписанные коммиты получают метку верификации в интерфейсе.

## 2.2. Git

- **Быстрый старт / Обзор** — установка Git, первичная конфигурация (`user.name`, `user.email`), базовый рабочий цикл.
- **Справочная документация**: работа с терминалом, редактирование в консоли (nano/vim), работа с файлами и директориями, шпаргалка по командам Git, изменение URL удаленного репозитория (`git remote set-url origin ...`), FAQ.

## 2.3. Репозитории

### Быстрый старт и обзор

Создание репозитория (личный/организационный), видимость, инициализация README/.gitignore/лицензией, шаблоны.

### Жизненный цикл репозитория (практические руководства)

- **Клонирование** — SSH/HTTPS.
- **Импорт** — из GitHub, GitLab, Gitea и др.; для приватных источников нужен токен; иногда нужно убрать `.git` из ссылки. Лимиты импорта: до 16 ГБ, до ~1 часа.
- **Зеркалирование** — автоматическая синхронизация с внешним репозиторием (интервал ~8 ч). ВАЖНО: для зеркальных репозиториев недоступен CI/CD.
- **Форк** — копия репозитория в своем аккаунте для независимой работы и запросов на слияние в оригинал.
- **Репозиторий-шаблон** — чекбокс «Сделать репозиторий шаблоном»; используется, в т.ч., в GitVerse Lab.
- **Переименование** — старые URL перенаправляются, но локальные remote лучше обновить.
- **Передача другому владельцу** — transfer с подтверждением нового владельца; лимит Git LFS при передаче не пересчитывается (старые LFS-файлы остаются в квоте прежнего владельца, новые загрузки расходуют квоту нового).
- **Архивация** — репозиторий становится read-only; разархивация возможна (только владелец).
- **Удаление** — необратимо, требует ввода названия для подтверждения.

### Работа с ветками

- **Создание ветки** — из интерфейса или `git checkout -b`.
- **Коммиты** — просмотр истории, граф коммитов.
- **Смена главной ветки** — в настройках репозитория.
- **Теги** — создание, просмотр; **защита тегов** от удаления/перезаписи.

### Запросы на слияние (PR)

- **Создание** — выбор head/base веток, описание, ревьюеры, исполнители, метки, связь с задачами.
- **Черновик (draft)** — запрос-заготовка, не готовый к слиянию.
- **Совместное ревью** — комментарии к строкам кода, предложения правок, треды обсуждений, закрытие обсуждений (resolve).
- **Упоминания** пользователей (@user) и команд (@org/team) — приходят уведомления.
- **Обязательные проверки CI/CD** — запрос нельзя слить, пока не пройдут обязательные статус-проверки.
- **Слияние** — стратегии merge/squash/rebase; удаление ветки после слияния.
- **Защита веток** — запрет force push, запрет удаления, обязательное ревью, обязательные проверки; защита всех веток автоматически запрещает force push.
- **Дашборд запросов** и вкладка «Запросы» в репозитории — фильтры, поиск.

### Настройка репозитория

- Вкладки: Репозиторий (основные параметры, передача, архивация, удаление), Ветки (главная ветка, защита), Секреты (CI/CD-секреты), Раннеры (self-hosted), Лимиты, **AI-Соавторы** (подключение GigaCode-агента и GigaCode-разработчика).

### Настройка репозитория для команды

- **Соавторы** — внешние пользователи с доступом к конкретному репозиторию (чтение/запись/администрирование); приватный пользователь не ищется в подсказках, но добавляется по точному имени.
- **Видимость репозитория** — публичный/приватный; в приватной организации публичный репозиторий становится внутренним.
- **Ревью владельцами кода (CODEOWNERS)** — файл CODEOWNERS задает владельцев частей кода; приоритет расположения: `/.gitverse/` > `/` > `/docs/`; владельцы автоматически назначаются ревьюерами.

### Работа с файлами

- Веб-редактор: создание/правка/удаление файлов и папок, загрузка файлов (лимиты: 5 МБ на файл и 50 МБ суммарно через веб; 100 МБ на файл в коммите по HTTPS, 1 ГБ по SSH).
- **Поиск по коду** — по содержимому внутри репозитория.
- **Git LFS** — для больших файлов: лимит 2 ГБ/мес на пользователя или организацию, файл ≤100 МБ (HTTP) / ≤1 ГБ (SSH); индикация расхода (зеленый <75%, оранжевый 75–90%, красный >90%); просмотр в Настройки → Лимиты.
- **Подмодули** — работа с git submodules.

### Стандарты оформления репозитория

- Файлы README, LICENSE, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY и др.; приоритет расположения: `.gitverse` > `.github` > `/` > `docs`.
- **Категории репозиториев** — группировка в профиле организации.
- Топики: до 25 тем, ≤35 символов каждая.

### Справочная документация

- **GitVerse Migration Tool** — утилита миграции с флагами для переноса репозиториев (включая LFS, вики, задачи).
- **Разметка текстовых файлов**: Markdown (+HTML-теги kbd/p/ul/ol/code/hr), LaTeX-формулы `$...$` и `$$...$$`, Mermaid-диаграммы (flowchart, sequence, gantt, ER); **AsciiDoc (.adoc)**: заголовки `=`/`==`/`===`, блоки `[source]`, `[quote]`, списки `*`/`-`, чекбоксы `[ ]`/`[x]`, таблицы `|===`, `include::`, атрибуты (`:toc:`).
- **Работа с Python** — особенности отображения/выполнения.
- **Зеркала репозиториев на GitVerse** — каталог зеркал популярных проектов.
- **Удаление конфиденциальных данных** — переписывание истории (git filter-repo / BFG), ротация скомпрометированных секретов.
- **FAQ**.

## 2.4. Задачи (классические) и Задачи 2.0

### Обзор и быстрый старт

- Трекер задач включается в репозитории; «Мои задачи» — агрегатор по всем репозиториям; фильтры сохраняются в URL; метки с цветами; подзадачи скрыты по умолчанию (фильтр «Тип»).
- **Задачи 2.0** — развитая модель: типы задача/эпик/история/дефект/подзадача; код задачи вида `TSKSTR-007`.

### Практические руководства

- **Композиция задач** — связи «состоит из» / «является частью» / «связано с»; иерархия эпик → история → задача → подзадача.
- **Связь задач и кода** — ручное и автоматическое прикрепление веток и запросов на слияние: по имени ветки, имени MR, regex-коду задачи в сообщении коммита (`\w+/{taskCode}`).
- **Проекты** — объединение задач в проекты.

### Справочная документация

- Ролевая модель репозиториев организации в контексте задач.

## 2.5. Вики

- Иерархическая вики-документация репозитория, WYSIWYG-редактор, история версий страниц.
- Ролевая модель: Чтение / Запись / Администратор.
- Обзор, быстрый старт, справочная документация.

## 2.6. Сканирование безопасности (DevSecOps)

### Обзор

Комплекс проверок: уязвимости зависимостей (CVE), лицензионные риски, секреты в коде. Принцип Shift-Left — проверки при PR и при push.

### Быстрый старт

Включение сканирования в Настройки → Безопасность, активация автопроверок PR и защиты от утечки секретов.

### Практическое руководство

- **Анализ безопасности репозитория** — вкладка «Безопасность»: уязвимости CVE с графом зависимостей, лицензии, **автоматическая гидратация** (реальная установка зависимостей перед анализом для точного выявления транзитивных уязвимостей; 6 основных экосистем, включая Python, Node.js, PHP, Go); **экспорт/импорт SBOM** в формате CycloneDX 1.6 JSON (файл ≤50 МБ) для визуализации отчетов сторонних сканеров; среднее время полного сканирования ~10 минут.
- **Защита от утечки секретов (Push Protection)** — сканирование при `git push` и блокировка отправки при находках; работает для всех языков без настройки; если секрет удален новым коммитом, push все равно блокируется, т.к. секрет остается в истории — нужно переписать историю (`git commit --amend`, `git rebase -i`); ложные срабатывания размечаются по ссылке из терминала («Ложное срабатывание»/«Тестовые данные») — блокировка снимается. Доступность: личные репозитории (в раннем доступе бесплатно; далее приватные — в GitVerse Pro), для организаций — ожидается.

### FAQ

Сроки, гидратация, экосистемы, ограничения (см. выше).

# 3. Вкладка «CI/CD»

## 3.1. Введение и быстрый старт

- Workflow описываются YAML-файлами в каталоге **`.gitverse/workflows/`** (раннер также читает `.github/workflows/` для совместимости).
- Синтаксис совместим с GitHub Actions: `name`, `run-name`, `on`, `env`, `jobs`, `steps`, `uses`, `run`, `strategy`, `container`.
- Быстрый старт: создать `.gitverse/workflows/ci.yml` с триггером `on: push`, job на `runs-on: ubuntu-latest`, шаги `actions/checkout@v4` + команды.

## 3.2. Справочная документация

### Синтаксис workflow (полный разбор)

- `name` / `run-name` — имя workflow и отображаемое имя запуска.
- `on` — события-триггеры (см. ниже).
- `env` — переменные окружения на уровнях workflow/job/step.
- `jobs.<id>` — задачи: `runs-on` (метки раннеров), `needs` (зависимости), `if` (условия), `steps` (`uses` — экшен, `run` — shell-команды, `with`, `env`, `id`, `name`), `outputs` (через `$GITVERSE_OUTPUT`), `timeout-minutes` (по умолчанию 15 мин облачные / 3 часа self-hosted), `container` (запуск job в контейнере), `strategy`.
- `strategy.matrix` — матрица конфигураций: **максимум 256 задач**, `include`/`exclude`, `fail-fast`, `max-parallel`.
- Контексты `${{ ... }}`: `gitverse`, `github`, `env`, `job`, `jobs`, `runner`, `secrets`, `strategy`, `matrix`, `steps`, `inputs`, `vars`.

### Триггеры запуска

- **Полностью поддерживаемые**: `create`, `delete`, `fork`, `push`, `release`, `schedule`, `workflow_call`, `workflow_dispatch`.
- **Частично поддерживаемые**: `pull_request`, `pull_request_review`, `pull_request_review_comment`, `pull_request_target`.
- **Неподдерживаемые (~20)**: `issues`, `workflow_run`, `repository_dispatch`, `registry_package` и др.
- `schedule` (cron): минимальный интервал **15 мин на облачных** / **5 мин на self-hosted** раннерах.
- `workflow_dispatch` — ручной запуск с `inputs` (string, boolean, choice и др.).

### Контексты и выражения

Доступ к данным события (`gitverse.event.*`), репозиторию (`gitverse.repository`), актору (`gitverse.actor`), выходам шагов и задач, секретам и переменным.

### Секреты и переменные

- Задаются на уровне репозитория или организации (организационные доступны всем ее репозиториям).
- Секреты маскируются в логах (`****`); имена **не чувствительны к регистру**; запрещены префиксы `GITHUB_`, `GITLAB_`, `GITEA_`, `GITVERSE_`; приоритет: репозиторий > организация.
- Переменные — через контекст `vars`, секреты — через `secrets`; токены для внешних систем передавать только через секреты.

### Лимиты CI/CD (облако)

- Минуты сборки: 500 мин/мес приватные репозитории, 1000 мин публичные; верифицированные организации — 1000/2000.
- Максимум 30 мин на job (облако); артефакты: 500 МБ всего, хранение 30 дней (настраивается `retention-days`).
- CI/CD недоступен для зеркальных репозиториев.
- Docker-экшены на глобальных раннерах кэшируются — рекомендуется использовать composite-экшены.

### Раннеры

- **Облачные**: метка `ubuntu-latest`; эфемерные окружения; **нет доступа к docker.sock** (сборку образов выполнять через kaniko); нет доступа к локальным сетям.
- **Self-hosted**: на базе act_runner; команды `register`, `daemon`, `generate-config`; метки вида `self-hosted:host`, `img-ubuntu-20.04:gitverse:gitverse/runner-image:ubuntu-20.04`; параметр capacity (параллельность); установка как systemd unit. ВАЖНО: сентябрьский релиз 2026 прекращает поддержку endpoint `gitverse.ru/sc` — раннеры нужно перерегистрировать с `gitverse.ru` и очистить каталог `/.cache/`.
- **Организационные раннеры**: общий раннер для всех репозиториев организации с политикой безопасности по видимости/владельцу репозитория.

## 3.3. Практические руководства

- **Артефакты** — upload/download между job, хранение, скачивание.
- **Кэширование** — actions/cache для зависимостей.
- **Матричные пайплайны** — примеры matrix-сборок.
- **Интерфейс CI/CD** — страница запусков, логи, перезапуск, фильтры.
- **Уведомления** — о результатах запусков.
- **Шаблоны workflow** — готовые шаблоны из репозитория шаблонов.
- **Защита веток через CI/CD** — обязательные статус-проверки.
- **Деплой** — на Cloud.ru и в Kubernetes.
- **Maven** — сборка и публикация пакетов из CI.
- **Rustore** — публикация мобильных приложений в RuStore из CI (`cicd-rustore`).
- **release-action** — создание релизов из workflow.
- **delete-old-packages-action** — очистка пакетов: хранит 100 последних версий, параметры `keep`, `semver-pattern`/`version-pattern`, `dry-run`.

# 4. Вкладка «Хранение артефактов» (Пакеты и релизы)

## 4.1. Пакеты (реестр пакетов)

Сервис хостинга пакетов в публичном и приватном режиме. Общий лимит: **500 МБ совокупно** на пользователя/организацию; срок хранения неограничен; при превышении — удалить старые версии или обратиться в поддержку. Поддерживаемые типы:

- **Maven** — `mvn deploy`; настройка `settings.xml` (сервер с токеном) + `pom.xml` (distributionManagement → `gitverse.ru/api/packages/<user>/maven/`).
- **Docker** — `docker login gitverse.ru`, `docker push gitverse.ru/<user>/<image>:tag`; теги регистронезависимы.
- **DEB** — APT-репозитории по distribution/component; загрузка PUT-запросом; `repository.key` для подписи; уникальность = имя+версия+архитектура+distribution+component.
- **RPM** — root/grouped структуры; подключение через `dnf config-manager`, при необходимости `--nogpgcheck`.
- **Generic** — произвольные файлы через `curl -X PUT` (zip, pdf, csv и др.).
- **Go** — zip с каталогом вида `модуль@версия`.
- **Helm** — загрузка через curl / cm-push / OCI (`helm push oci://gitverse.ru/<user>`).
- **npm** — `.npmrc` (registry + `_authToken`), `npm publish` / `unpublish` / `dist-tag`.
- **NuGet** — `dotnet nuget add source`, `dotnet nuget push`.
- **PyPI** — `.pypirc` + `twine upload`, форматы `.tar.gz`/`.whl`.

## 4.2. Зеркала реестров

Готовые зеркала внешних репозиториев пакетов (суффикс `.gitverse.ru`): **dh-mirror** (Docker Hub), **mvn-mirror**, **npm-mirror**, **pypi-mirror**, **go-mirror**, **crates-mirror**. Предоставляются «как есть», без контроля содержимого; подключаются заменой registry/репозитория в конфигурации инструмента.

## 4.3. Релизы

- Релиз создается на основе **тега** (обязателен); чекбоксы: «предварительный релиз», «заголовок в сообщение тега», «ограничение доступа неавторизованным».
- **Ассеты** — файлы к релизу (форматы .7z, .apk, .zip, .whl и др.); уникальные имена; счетчик загрузок. Лимиты: суммарно 4 ГБ на пользователя/организацию; один файл ≤100 МБ; до 5 файлов за загрузку; ≤500 МБ за одну загрузку; срок хранения неограничен.
- Автоматизация: `release-action` в CI/CD.

# 5. Вкладка «AI»

## 5.1. GigaCode для IDE и CLI

### Базовые понятия

- **Режимы**: **Ask** (вопросы по коду без изменений), **Agent** (агентный режим — читает, изменяет файлы, выполняет команды), **Plan** (планирование без правок).
- **Команды**: `/` — служебные команды; `@` — добавление файлов/директорий в контекст; `#` — кастомные промпты.
- **GIGACODE.md** — файл инструкций: корень репозитория; `~/.gigacode/GIGACODE.md` (глобальный); `.gigacode/GIGACODE.local.md` (локальный); также читается `AGENTS.md`.
- **Rules** — правила: `.gigacode/rules/` (проектные), `~/.gigacode/rules/` (глобальные); YAML frontmatter `apply: ALWAYS/OFF`, `mode: AGENT/ASK/ALL`.
- **Skills** — папка + `SKILL.md` (kebab-case; frontmatter `name`, `description`, `priority`, `paths`, `user-invocable`, `disable-model-invocation`); каталоги `~/.gigacode/skills/` и `.gigacode/skills/`.
- **Субагенты** — `.gigacode/agents/` и `~/.gigacode/agents/`; frontmatter `name`, `description`, `model: inherit|fast|<id>`, `approvalMode: default|plan|auto-edit|bubble`, `tools`/`disallowedTools`; fork-субагент наследует контекст, работает в фоне; prompt cache дает ~80% экономии.
- **MCP** — подключение внешних инструментов: типы stdio/http/sse; настройка в `settings.json` (`mcpServers`) или `gigacode mcp add`; `trust: true` пропускает подтверждения; `includeTools`/`excludeTools`; OAuth-поля; токены в `~/.gigacode/mcp-oauth-tokens.json`; timeout по умолчанию 600000 мс, discoveryTimeoutMs: stdio 30 с / http 5 с.
- **Модели** — think/fast/code; 30+ моделей из Cloud.ru; поддержка 35+ языков.

### Начало работы / Работа с кодом

Установка плагина (VS Code, JetBrains/GigaIDE, Android Studio, Jupyter), авторизация через GitVerse, первая задача (начать с простого сценария без изменения файлов, затем план → реализация → тесты). Обновления плагина проверяются каждые 6 часов; статус Ready на нижней панели.

### GigaCode CLI

- Команды: `/init` (создать GIGACODE.md/AGENTS.md), `/summary`, `/compress` (сжатие контекста), `/resume`, `/restore`, `/context`, `/plan`, `/approval-mode`, `/model`, `/agents create|manage`, `/skills`, `/mcp`, `/memory`, `/btw` (побочный вопрос).
- **Memory** — память агента между сессиями.
- **Skills / Субагенты / MCP** — как в базовых понятиях.

### GigaCode для GigaIDE (JetBrains) и для VS Code

- Для каждой IDE: установка, настройки (контрольные точки, уведомления, управление контекстом, язык интерфейса), свои страницы MCP/Rules/Skills.
- VS Code: основная папка настроек `.gigacode_vsc` с файлом `gigacode.jsonc` (частично поддерживается и `.gigacode`); MCP-типы HTTP/SSE/локальные (command/args/env/cwd); готовые jira MCP и confluence MCP (зависит от настроек организации). Rules/Skills создаются через настройки плагина + файлы markdown с frontmatter (`name`/`description` обязательны).

## 5.2. AI-разработка на GitVerse (методология)

- **AI-агент** = языковая модель + инструменты + окружение с кодом. Ключевые следствия: ставить задачу, а не инструкцию; агент работает циклом и сам себя проверяет; все, чего агент не знает, он додумает — главный источник ошибок. Результат = контекст + инструменты + проверка.
- **Первая задача** (~30 мин): открыть сессию → `/init` (генерация AGENTS.md, вычистить общие советы и закоммитить) → задача в режиме Plan с просьбой задать уточняющие вопросы → проверка плана (границы + способ проверки) → выполнение в Build → требовать вывод проверки, а не словесный отчет.
- **Подготовка репозитория**: AGENTS.md — открытый стандарт; писать только то, о чем агент ошибется без подсказки (точные команды сборки/тестов/линтера, границы модулей, особенности инструментов и тестов, договоренности, требования к коммитам); ~30 строк — норма; вложенные AGENTS.md в поддиректориях (для монорепо); `/init` повторять после крупных изменений.
- **Цикл работы** (5 шагов с проверками перехода): Контекст (описать задачу целиком) → Уточнение (вопросы агента) → Исследование (каждое утверждение — со ссылкой файл:строка) → План (цель, файлы, границы, критерии приемки, команда проверки) → Выполнение (проверка показана, а не заявлена). Типичные ошибки: задача одной строкой, пропуск уточнения, нет границ, «готово» без проверки, ревью без условия остановки.
- **Контекст**: окно ограничено; больше всего едят вывод команд и прочитанные файлы; автоматическое сжатие диалога (и ручное `/summarize`); после сжатия агент помнит выводы, но не дословную переписку — важное фиксировать в файлах. Приемы: новая задача = новый диалог; объемный поиск — субагенту; короткие инструкции; не просить «прочитать все»; фильтровать логи.
- **Инструменты и MCP**: агент умеет читать/изменять файлы, выполнять команды, вызывать субагентов, подключать навыки. Подтверждение действий: «спрашивать» (разрешить один раз / на всю сессию / отклонить с комментарием) или «автоматически» (права не расширяются). Запрещено профилем прав: чтение `.env`, `.key`, `.pem`, `.netrc`; изменение `.git` и служебных каталогов; `curl`, `wget`, `git merge`, `git reset --hard`.
- **Навыки**: процедуры, подключаемые по мере надобности; `.agents/skills/<имя>/SKILL.md` с обязательными `name`/`description` (description — условие применения); имена уникальны; рядом можно класть скрипты/шаблоны; экономия контекста (видны только имя+описание). Что куда: действует всегда → AGENTS.md; нужно иногда/длинное/пошаговое → навык.
- **Агенты и субагенты**: встроенные Build (полные права) и Plan (только чтение); встроенные субагенты `explore` (поиск, read-only) и `general`; собственные агенты — markdown в `.opencode/agent/` с frontmatter (`description`, `mode: primary|subagent|all`, `permission` (allow/ask/deny по инструментам и шаблонам), `temperature`, `steps`). Навык или агент: процедура → навык; ограничение прав/отдельная роль → агент; изоляция исследования → субагент.

## 5.3. GigaCode на GitVerse (веб-интерфейс)

- **GigaCode-ассистент** — чат (кнопка GigaCode в правом нижнем углу; только для авторизованных): ответы по платформе со ссылками на документацию, анализ репозитория, Git-операции (создание/изменение/удаление файлов, коммиты, запросы на слияние, создание репозитория); контекст определяется автоматически на уровне репозитория; встроенные навыки платформы (до 3 на сообщение; собственные навыки репозитория в чате не работают); режимы «Спрашивать перед изменениями» (по умолчанию) / «Изменять автоматически»; виды чата: всплывающее окно / боковая панель / весь экран; история чатов с поиском и удалением.
- **GigaCode-агент** — AI-ревьюер в запросах на слияние; подключается владельцем/Owners (Настройки → AI-соавторы, при создании или в открытом запросе); добавляется в соавторы и ревьюеры (вручную не удалить); команды в комментариях: `/describe` (описание изменений; объединяется с описанием пользователя), `/review` (сложность, тесты, риски, рекомендации), `/improve` (предложения по улучшению с оценкой важности), `/ask` (вопросы по запросу); все три команды запускаются автоматически в новых запросах при включенном агенте. **Правила ревью** — markdown-файлы в `.gitverse/pr_rules/` целевой ветки (конкретные проверяемые правила, контекст стека, примеры «до/после», ожидаемое поведение, инструменты, тестовые сценарии). Ограничения: после новых коммитов команды нужно повторять; в закрытых запросах не работает; вне запросов на слияние не поддерживается.
- **GigaCode-разработчик** (ограниченный доступ) — AI-исполнитель: включение в Настройки → AI-соавторы; три способа передать задачу — назначить исполнителем задачи («Назначить GigaCode»), упоминание в комментарии к задаче, упоминание в комментарии к запросу на слияние (правки в тот же запрос); ход работы виден в AI-сессии; по завершении — комментарий с итогом и ссылкой на запрос; использует навыки из `.agents/skills`.
- **Сессии** (ограниченный доступ) — диалог с агентом в облачном окружении с репозиторием: до 10 репозиториев на сессию, выбор ветки; стадии запуска окружения; агенты build/plan (собственные агенты/команды/навыки появляются после запуска окружения); встроенные команды `/init`, `/review`; карточки вопросов и планов; подтверждение действий; индикатор контекстного окна и сжатие; остановка генерации; список сессий сгруппирован по репозиториям (состояния: Запускается/Восстанавливается/Нужен ответ/Нужно разрешение); после ~15 мин бездействия окружение останавливается (переписка сохраняется, следующее сообщение поднимает окружение; неотвеченные запросы устаревают); сессия видна только автору.
- **AI workflow-сценарии** — запуск AI-агента из CI/CD: экшен `actions/ai-developer-action@master`; обязательные элементы: `actions/checkout@v4`, сам AI-экшен, `prompt` или `prompt_file`; подстановки `${{ gitverse.repository }}`, `${{ gitverse.event.issue.number }}`, `${{ gitverse.event.issue.title }}`, `${{ gitverse.actor }}`; авторство действий: по умолчанию от имени владельца репозитория, изменяется `git_token`, `commit_author_name`, `commit_author_email`; **собственная модель** (OpenAI-совместимая): `model_base_url`, `model_name`, `model_api_key`; **внешние MCP** через `mcp_config` (типы local/remote, инструменты с префиксом `<сервер>_<инструмент>`, фильтры `include_tools`/`exclude_tools`); собственные инструкции `AGENTS.md` и навыки `.agents/skills` (общие наборы — из отдельного репозитория с `ref`, исключить через `.git/info/exclude`); собственные агенты сценария в `.ai-action/opencode/agents/*.md` + параметр `opencode_agent`; лимиты контекста: `model_context_limit` (по умолчанию 254000), `model_output_limit` (30000).
- **Генерация сообщения коммита** — кнопка «Сгенерировать» в окне создания коммита; заполняет Сообщение и Описание; отметка «Создано с помощью GigaCode».
- **Разбор ошибок CI/CD** — блок «Разбор ошибок с GigaCode» в упавшей задаче запуска: причина, ключевые строки, рекомендации; кнопка «Исправить с помощью ИИ» открывает чат ассистента с готовым промптом.

## 5.4. GitVerse MCP

- Удаленный MCP-сервер платформы: endpoint **`mcp.gitverse.ru`**, HTTP, заголовок `Authorization: Bearer <токен>` (тот же токен, что для Публичного API; без заголовка — 401).
- Ручной обмен: `initialize` → сервер возвращает `Mcp-Session-Id` (передавать далее) → `notifications/initialized` → `tools/list` → `tools/call`; данные в `result.content[0].text` (JSON-строка с объектом Result).
- **42 инструмента** по разделам: репозитории (list_branches, create_repository, get_repository, update_repository, fork_repository, create_branch, create_tag, get_repository_tree), файлы (get_repository_content, create_or_update_file, delete_file), коммиты (list_commits, get_commit), релизы (list/create/get_by_tag/get/update), запросы на слияние (create/list_files/update/list/read/update_branch), задачи (list_issues, issue_read, issue_write, add_issue_comment), CI/CD (get_workflow_dispatch_inputs, trigger_workflow_dispatch, actions_get, actions_list, get_job_logs, get_job_failure_context), пользователи и поиск (get_my_user_info, get_user_by_username, search_users), команды (get_teams, get_team_members), звезды (list_starred, star, unstar).

# 6. Вкладка «GitVerse Pages»

- Хостинг статических сайтов из репозиториев. Типы: сайт **пользователя/организации** (`owner.gitverse.site`, из репозитория с именем `owner.gitverse.site`) и сайт **проекта** (`owner.gitverse.site/repo`).
- **Требования**: публичный репозиторий, включенный CI/CD, логин владельца без точек (точки в имени репозитория заменяются дефисами), кастомные домены не поддерживаются (только `*.gitverse.site`), кастомная страница ошибок — `404.html`/`404.md` в корне.
- **Источник «Ветка»**: автоматическая сборка **Jekyll 3.9.\***; при отсутствии автоматически подставляются `Gemfile`, `_config.yml`, `_layouts/default.html`; сборка с `JEKYLL_ENV=production`; в шаблонах только относительные пути (`{{ 'path' | relative_url }}`); файл `.nojekyll` отключает обработку Jekyll; инфраструктура S3 + CDN + Nginx. Входной файл: `index.html` → `index.md` → `README.md` (по приоритету); поддерживаемые папки: `/`, `/docs`, `/site`, `/public`, `/out`.
- **Источник «Воркфлоу»**: деплой из CI/CD — экшены `gitverse/upload-pages-artifact@v1.0.0` (параметр `path`, артефакт ≤500 МБ, обязателен `index.html`, `retention-days` не менять — 1 день) и `gitverse/deploy-pages@v1.0.0`.
- Включение: Настройки репозитория → Pages → выбор источника.

# 8. Вкладка «Организации и корпорации»

## 8.1. Организации

- **Роли**: Владелец (команда Owners) и Участник; владелец имеет полный доступ ко всем ресурсам организации.

- **Соавторы** — внешние участники без членства в организации: вкладка Участники → Соавторы; при удалении соавтор исключается из всех репозиториев.
- **Верификация организации** — через обращение в поддержку; градиентная обводка + галочка; блокирует смену названия и ссылок.

## 8.2. Корпорации (Enterprise)

- Создаются через поддержку (ограниченный доступ); роли: администраторы, участники, внешние соавторы.
- Возможности: журнал аудита, видимость корпорации только администраторам, исключение участников и организаций, выгрузка данных в CSV.

- Git LFS: 2 ГБ/мес на пользователя/организацию; при передаче репозитория квота LFS не пересчитывается (остается у прежнего владельца).

# 10. Вкладка «Сообщество»

## 10.1. GitVerse Lab (бывш. SmartClass) — образовательная платформа

- **Модули** — учебные курсы: публичные и приватные.
- **Задания**: индивидуальные и групповые (тип после создания изменить нельзя); из репозитория-шаблона создается снепшот → форк для каждого участника; переиспользование заданий между модулями.
- **Дедлайны**: мягкие (информационные) и жесткие (репозиторий → read-only, задание деактивируется; возможны исключения для отдельных участников; реактивация = новая дата + статус «Активное»).
- **Автопроверки**: конструктор «ввод-вывод» или «команда запуска», либо YAML-воркфлоу с экшенами `autograding-io-grader@v2` и `autograding-grading-reporter@v2`; конфигурация `smartclass.yml` защищается через защиту веток.
- **Импорт участников**: списком, CSV или XLSX (≤5 МБ); операция идемпотентна.

## 10.2. Поддержка

- Каналы: форма обратной связи, шаблон bug_report в задачах, почта support@gitverse.ru.
- **HAR-файлы** для диагностики: записываются в DevTools браузера; передавать только официальной поддержке; после записи перелогиниться (в HAR сохраняются сессионные данные).

# 11. Вкладка «Разработчикам»

## 11.1. OAuth 2.0

- Поддерживается **только Authorization Code Flow с PKCE** (S256, обязателен для всех клиентов); implicit, client credentials, device grant не поддерживаются.
- Приложения: личные и организационные; клиенты конфиденциальные (с секретом) и публичные.
- Endpoints: `GET /signin/oauth/authorize` и `POST /login/oauth/access_token`.
- Код авторизации одноразовый, живет 10 минут (префикс `gta_`); access_token — JWT RS256, 1 час; refresh_token — 30 дней с ротацией (расхождение счетчика → инвалидация всех токенов семейства).
- `redirect_uri`: точное совпадение, без wildcard, HTTPS в production, `127.0.0.1` для локальной разработки.
- **Scopes**: `read:`/`write:` × `repository`/`user`/`organization`/`package` (write включает read); `state` — защита от CSRF.
- Ошибки: `invalid_request`, `invalid_client`, `unauthorized_client`, `unsupported_response_type`, `invalid_scope`, `access_denied`, `invalid_grant`, `unsupported_grant_type`.
- Секрет приложения показывается один раз; регенерация не отзывает активные токены; отзыв грантов пользователем — в настройках.

## 11.2. Маркетплейс

- Витрина навыков (skills): `gitverse.ru/services/marketplace`.
- Установка: `npx skills add {repo-url} --skill {skill-name}` → `.agents/skills/`; управление: `npx skills list`, `npx skills remove`.

## 11.3. Публичный API

- Базовый URL: `api.gitverse.ru`; заголовки `Authorization: Bearer TOKEN` и `Accept: application/vnd.gitverse.object+json;version=1`; пагинация через заголовок `Link`.
- Группы эндпоинтов: **CI/CD** (actions: runs, jobs, logs, artifacts, runners, secrets, variables, dispatches), **Соавторы**, **Git Database** (commits, trees), **Миграция**, **Команды и организации**, **Пакеты**, **Задачи 2.0 и запросы на слияние**, **Вебхуки**, **OAuth** (~150 операций; подробные спецификации — на gitverse.ru/docs/developers/public-api).
